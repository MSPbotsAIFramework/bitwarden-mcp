## Requirement understanding

One line: Create a text Bitwarden Send in the client's own Bitwarden from a secret the agent passes in, with an expiry and a maximum access count, and return the Send link, without storing or logging the secret.

Sources: ticket description and the [INTAKE · PRD-22483] comment (MicusAI, 2026-11-25, carries the Done when list); code MSPbotsAIFramework/bitwarden-mcp@fee1516; Bitwarden client source (bitwarden/clients `libs/common/src/tools/send/services/send.service.ts`, read 2026-11-25); wiki: not covered (`mbp.py wiki find bitwarden` and `wiki find "Bitwarden Send"` returned no hit; docs.mspbots.ai/connectors/bitwarden/ returns 404).

Restatement:
- What: one new connector tool that creates a text-type Bitwarden Send with a set expiry and access limit, and returns its share link.
- For whom: VIP IT (vipitinc.com) service-desk technicians who run the SOP Agent for retail-staff onboarding, about 38 onboardings a month.
- Why: today the technician creates the Send by hand after the M365 account is created; that manual step breaks end-to-end automation. VIP IT wants delivery from its own Bitwarden, not One-Time Secret / Password Pusher.
- Success: in a supervised pilot the agent hands over the credentials as a Bitwarden Send link from VIP IT's own Bitwarden; the link opens the secret, stops working at the access limit and at expiry, the Send is visible in VIP IT's Bitwarden, and the secret never shows up in a log, tool result or run detail.

## Current state (every claim carries path:line)

All paths at MSPbotsAIFramework/bitwarden-mcp@fee1516 unless stated.

- A Bitwarden connector already exists and is the only Bitwarden repo in MSPbotsAIFramework (`bitwarden`, `bitwarden-send-mcp`, `bw-mcp` do not exist). It covers organization member and group management only: tools in `src/bitwarden_mcp/tools/members.py` and `src/bitwarden_mcp/tools/groups.py`, registered at `src/bitwarden_mcp/server.py:156-159`.
- Bitwarden Send is explicitly out of scope today: README.md "Out of scope" paragraph and "Known Limitations" ("No Bitwarden Send support"). The README's reason: the Public API cannot manage vault items, and Send needs an unlocked vault.
- Authentication is the organization API key only: `client_credentials` with `scope=api.organization` (`src/bitwarden_mcp/api_client.py:10`, `:41-59`). The token is fetched per call and never cached (`api_client.py:61-66`).
- Gateway credentials come from four headers (`src/bitwarden_mcp/config.py:33-36`); `/mcp` requests without `x-bitwarden-client-id` and `x-bitwarden-client-secret` get 401 (`src/bitwarden_mcp/server.py:88-103`). Credentials are held in a per-request contextvar (`server.py:28-30`, `:105-116`).
- Errors are returned as `"Error: ..."` strings (`src/bitwarden_mcp/tools/members.py:32-33`); token-exchange errors include the Bitwarden response body (`api_client.py:53-58`).
- The repo has no `tests/` directory; dev deps already list pytest, pytest-asyncio, respx (`pyproject.toml`).
- Why the org key cannot create a Send (Bitwarden client source, `send.service.ts`, `encrypt()`): a Send is end-to-end encrypted. The client makes a random 16-byte seed, derives the Send key with HKDF (salt `bitwarden-send`, purpose `send`), encrypts the name and text with that key, and stores the seed encrypted with the **user's** vault key (`send.key = encryptBytes(model.key, userKey)`). The share link carries the seed in its URL fragment. A Send belongs to a user, not to an organization, and the user key can only be unlocked with that user's master password. So creating a Send statelessly needs, per request: a user API key (to log in) and the master password (to unlock the user key).
- Platform side (read only): the agent runtime masks tool-call arguments whose name contains `secret`, `password`, `token` and similar (`mb-platform-agent@c5da2b788 shared/sensitive-args.ts:9-21`, mirroring `agentos/middlewares/redact.py` `SENSITIVE_NAMES` documented in `mb-platform-agentos@439e264 docs/modules/approval-redaction.md:9`).

## Product design

### Goals / Non-goals

Goals:
- New tool `bitwarden_create_text_send` in the existing Bitwarden connector: input a secret, an expiry and an access limit; output the Send link and its metadata.
- The Send is created in the client's own Bitwarden account (US cloud, EU cloud or self-hosted), so it shows up in that account's Send list for audit.
- The secret and the unlock credentials never appear in the tool result, in error messages or in the connector's logs.
- The existing nine member/group tools keep working unchanged for tenants that only have the organization API key.

Non-goals (not asked for in the ticket):
- Generating the secret inside the connector (the ticket's intake comment says the agent passes the secret in).
- File Sends, Send passwords, email-restricted Sends, listing / editing / deleting Sends.
- Changing how the platform stores credentials or renders run detail.

### Acceptance criteria AC1..AC7

- AC1 (DW1): Given valid Send credentials, when the agent calls `bitwarden_create_text_send` with a secret, an expiry in hours and a maximum access count, then a text Send is created with exactly that expiry and access count, and the tool returns a link that opens the secret.
- AC2 (DW2): The returned link stops showing the secret after the access count is reached, and after the expiry time.
- AC3 (DW3): The created Send is listed in the Send list of the Bitwarden account whose credentials were used, with the expiry and access count shown there.
- AC4 (DW4): The tool result contains the link and metadata only; neither the secret nor the master password appears in the tool result, in any error message, or in the connector's log output; the secret argument is named so the platform masks it in run detail.
- AC5 (DW1): Out-of-range input (expiry below 1 hour or above 720 hours, access count below 1 or above 100, empty secret or a secret longer than 1000 characters) returns a structured error and creates nothing.
- AC6 (DW1): Missing Send credentials, a wrong master password, or a Bitwarden-side rejection return a structured error that says which of these it is, and create nothing.
- AC7 (DW1): Tenants that only configured the organization API key see no change in the nine existing tools; a tenant that only configured the Send credentials can list tools and use the Send tool.
- DW5 (connector wiki page) is a release-step deliverable of the review leg (mcp-track.md 4.5), covered by TC-BWS-011.

### Open questions

- OQ1 (does not block implementation; assumption written): "Audited in VIP IT's Bitwarden" is read as "the Send appears in the Send list of the Bitwarden account used by the connector". Bitwarden Sends belong to a user, not to the organization, so the recommended set-up is a dedicated member account in VIP IT's organization (for example an "onboarding bot" user) whose Send list is the audit trail. If VIP IT needs the Send to appear in the organization's event log instead, that is not offered by Bitwarden for Sends and would need a product decision.
- OQ2 (does not block implementation; assumption written): default expiry 24 hours and default access count 1 when the agent does not pass them; the ticket asks only that they are "configurable / as set".
- OQ3 (control plane, handed to Leo Yang, not a product question): the connector needs three new credential fields on the already registered `bitwarden` vendor, one of them a master password. See Tech design "Risks & dependencies".
