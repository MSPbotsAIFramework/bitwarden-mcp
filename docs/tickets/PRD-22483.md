## Requirement understanding

One line: Create a text Bitwarden Send in the client's own Bitwarden from a secret the agent passes in, with an expiry and a maximum access count, and return the Send link, without storing or logging the secret.

Sources: ticket description and the [INTAKE · PRD-22483] comment (MicusAI, 2026-11-25, carries the Done when list); code MSPbotsAIFramework/bitwarden-mcp@fee1516; Bitwarden client source (bitwarden/clients `libs/common/src/tools/send/services/send.service.ts`, read 2026-11-25); wiki: not covered (`mbp.py wiki find bitwarden` and `wiki find "Bitwarden Send"` returned no hit; docs.mspbots.ai/connectors/bitwarden/ returns 404).

Restatement:
- What: one new connector tool that creates a text-type Bitwarden Send with a set expiry and access limit, and returns its share link.
- For whom: VIP IT (vipitinc.com) service-desk technicians who run the SOP Agent for retail-staff onboarding, about 38 onboardings a month.
- Why: today the technician creates the Send by hand after the M365 account is created; that manual step breaks end-to-end automation. VIP IT wants delivery from its own Bitwarden, not One-Time Secret / Password Pusher.
- Success: in a supervised pilot the agent hands over the credentials as a Bitwarden Send link from VIP IT's own Bitwarden; the link opens the secret, stops working at the access limit and at expiry, the Send is visible in VIP IT's Bitwarden, and the secret never shows up in a log, tool result or run detail.

## Current state (every claim carries path:line)

All paths at MSPbotsAIFramework/bitwarden-mcp@fee1516 unless stated.

- A Bitwarden connector already exists and is the only Bitwarden repo in MSPbotsAIFramework (`bitwarden`, `bitwarden-send-mcp`, `bw-mcp` do not exist). It covers organization member and group management only: tools in `src/bitwarden_mcp/tools/members.py` and `src/bitwarden_mcp/tools/groups.py`, registered at `src/bitwarden_mcp/server.py:156-159`.
- Bitwarden Send is explicitly out of scope today: README.md "Out of scope" paragraph and "Known Limitations" ("No Bitwarden Send support"). The README's reason: the Public API cannot manage vault items, and Send needs an unlocked vault.
- Authentication is the organization API key only: `client_credentials` with `scope=api.organization` (`src/bitwarden_mcp/api_client.py:10`, `:41-59`). The token is fetched per call and never cached (`api_client.py:61-66`).
- Gateway credentials come from four headers (`src/bitwarden_mcp/config.py:33-36`); `/mcp` requests without `x-bitwarden-client-id` and `x-bitwarden-client-secret` get 401 (`src/bitwarden_mcp/server.py:88-103`). Credentials are held in a per-request contextvar (`server.py:28-30`, `:105-116`).
- Errors are returned as `"Error: ..."` strings (`src/bitwarden_mcp/tools/members.py:32-33`); token-exchange errors include the Bitwarden response body (`api_client.py:53-58`).
- The repo has no `tests/` directory; dev deps already list pytest, pytest-asyncio, respx (`pyproject.toml`).
- Why the org key cannot create a Send (Bitwarden client source, `send.service.ts`, `encrypt()`): a Send is end-to-end encrypted. The client makes a random 16-byte seed, derives the Send key with HKDF (salt `bitwarden-send`, purpose `send`), encrypts the name and text with that key, and stores the seed encrypted with the **user's** vault key (`send.key = encryptBytes(model.key, userKey)`). The share link carries the seed in its URL fragment. A Send belongs to a user, not to an organization, and the user key can only be unlocked with that user's master password. So creating a Send statelessly needs, per request: a user API key (to log in) and the master password (to unlock the user key).
- Platform side (read only): the agent runtime masks tool-call arguments whose name contains `secret`, `password`, `token` and similar (`mb-platform-agent@c5da2b788 shared/sensitive-args.ts:9-21`, mirroring `agentos/middlewares/redact.py` `SENSITIVE_NAMES` documented in `mb-platform-agentos@439e264 docs/modules/approval-redaction.md:9`).

## Product design

### Goals / Non-goals

Goals:
- New tool `bitwarden_create_text_send` in the existing Bitwarden connector: input a secret, an expiry and an access limit; output the Send link and its metadata.
- The Send is created in the client's own Bitwarden account (US cloud, EU cloud or self-hosted), so it shows up in that account's Send list for audit.
- The secret and the unlock credentials never appear in the tool result, in error messages or in the connector's logs.
- The existing nine member/group tools keep working unchanged for tenants that only have the organization API key.

Non-goals (not asked for in the ticket):
- Generating the secret inside the connector (the ticket's intake comment says the agent passes the secret in).
- File Sends, Send passwords, email-restricted Sends, listing / editing / deleting Sends.
- Changing how the platform stores credentials or renders run detail.

### Acceptance criteria AC1..AC7

- AC1 (DW1): Given valid Send credentials, when the agent calls `bitwarden_create_text_send` with a secret, an expiry in hours and a maximum access count, then a text Send is created with exactly that expiry and access count, and the tool returns a link that opens the secret.
- AC2 (DW2): The returned link stops showing the secret after the access count is reached, and after the expiry time.
- AC3 (DW3): The created Send is listed in the Send list of the Bitwarden account whose credentials were used, with the expiry and access count shown there.
- AC4 (DW4): The tool result contains the link and metadata only; neither the secret nor the master password appears in the tool result, in any error message, or in the connector's log output; the secret argument is named so the platform masks it in run detail.
- AC5 (DW1): Out-of-range input (expiry below 1 hour or above 720 hours, access count below 1 or above 100, empty secret or a secret longer than 1000 characters) returns a structured error and creates nothing.
- AC6 (DW1): Missing Send credentials, a wrong master password, or a Bitwarden-side rejection return a structured error that says which of these it is, and create nothing.
- AC7 (DW1): Tenants that only configured the organization API key see no change in the nine existing tools; a tenant that only configured the Send credentials can list tools and use the Send tool.
- DW5 (connector wiki page) is a release-step deliverable of the review leg (mcp-track.md 4.5), covered by TC-BWS-011.

### Open questions

- OQ1 (does not block implementation; assumption written): "Audited in VIP IT's Bitwarden" is read as "the Send appears in the Send list of the Bitwarden account used by the connector". Bitwarden Sends belong to a user, not to the organization, so the recommended set-up is a dedicated member account in VIP IT's organization (for example an "onboarding bot" user) whose Send list is the audit trail. If VIP IT needs the Send to appear in the organization's event log instead, that is not offered by Bitwarden for Sends and would need a product decision.
- OQ2 (does not block implementation; assumption written): default expiry 24 hours and default access count 1 when the agent does not pass them; the ticket asks only that they are "configurable / as set".
- OQ3 (control plane, handed to Leo Yang, not a product question): the connector needs three new credential fields on the already registered `bitwarden` vendor, one of them a master password. See Tech design "Risks & dependencies".

## Tech design

### Conclusion

Add one tool, `bitwarden_create_text_send`, to MSPbotsAIFramework/bitwarden-mcp. Per request it logs in with a Bitwarden **user** API key, unlocks the user key with the master password in memory, builds an end-to-end encrypted text Send exactly the way Bitwarden's own clients do, posts it to `POST {api}/sends`, and returns the share link. Three new optional gateway headers carry the Send credentials; the existing organization-key headers become optional at the middleware so either credential set works. Nothing is cached, stored or logged. The vendor-repo work is self-contained, but the three new credential fields must be added to the `bitwarden` vendor already registered in the MCP control plane, which the pipeline's publish API cannot do; that part is handed to Leo Yang (see Risks & dependencies).

### Option analysis

| Option | Verdict |
|---|---|
| A. Stateless: user API key + master password headers, crypto done in-process per request | Chosen. Matches the vendor MCP contract (credentials only from headers, no state, request isolation). Bitwarden's protocol is open source and documented in its clients; the crypto is standard (PBKDF2/Argon2id, HKDF, AES-256-CBC + HMAC-SHA256). |
| B. Run the Bitwarden CLI (`bw send`) or `bw serve` inside the container | Rejected. Needs a logged-in, unlocked local vault: stateful, one account per container, breaks multi-tenant isolation; the README already rejects this for the same reason. |
| C. Organization Public API | Rejected. The Public API has no Send endpoints, and Sends belong to users, not organizations. |
| D. A separate new repo `bitwarden-send-mcp` registered as a new vendor | Rejected. Two repos for one product (the skill's naming rule is one `<vendor>-mcp`), and the pipeline cannot create repos (GitHub App has no admin permission). It would avoid the control-plane field change but splits one connector in two for users. |
| E. Third-party secret links (One-Time Secret, Password Pusher) | Rejected by the client in the ticket. |

### Data & API contract

Tool `bitwarden_create_text_send`:

```
Arguments
  secret              string, required, 1..1000 chars   the text to deliver (named "secret" so the platform masks it)
  expiration_hours    int, optional, default 24, 1..720
  max_access_count    int, optional, default 1, 1..100
  name                string, optional, default "Credentials", <= 100 chars   shown in the owner's Send list
  hide_text           bool, optional, default true       recipient must click to reveal
Result (JSON)
  {"send_id": "<uuid>", "access_id": "<accessId>", "link": "https://send.bitwarden.com/#/<accessId>/<seed b64url>",
   "expiration_date": "2026-11-26T08:00:00Z", "deletion_date": "2026-12-25T08:00:00Z",
   "max_access_count": 1, "name": "Credentials"}
Errors (JSON, no secret in any field)
  {"error": "invalid_argument", "field": "max_access_count", "message": "..."}
  {"error": "missing_credentials", "required_headers": ["x-bitwarden-user-client-id","x-bitwarden-user-client-secret","x-bitwarden-master-password"]}
  {"error": "authentication_failed", "message": "Bitwarden rejected the user API key (HTTP 400)"}
  {"error": "unlock_failed", "message": "The master password could not unlock the account key"}
  {"error": "unsupported_account", "message": "Account has no master password (SSO / Key Connector)"}
  {"error": "bitwarden_error", "status": 400, "message": "<Bitwarden message field>"}
```

Bitwarden request built by the tool (`POST {api}/sends`):

```
{"type": 0, "key": "2.<iv>|<ct>|<mac>"            (seed encrypted with the user key),
 "name": "2.<...>", "notes": null,
 "text": {"text": "2.<...>", "hidden": true}       (secret encrypted with the Send key),
 "maxAccessCount": 1, "expirationDate": "<now + expiration_hours, UTC ISO>",
 "deletionDate": "<now + 30 days, and never before expirationDate>",
 "password": null, "disabled": false, "hideEmail": false}
```

Link base: `x-bitwarden-api-url` default or `https://api.bitwarden.com` → `https://send.bitwarden.com/#`; `https://api.bitwarden.eu` → `https://vault.bitwarden.eu/#/send`; self-hosted `https://host/api` → `https://host/#/send`. Link = `<base>/<accessId>/<base64url(seed) without padding>`.

Headers (all optional at the middleware; at least one complete set required):

| Header | Required | Description |
|---|---|---|
| x-bitwarden-client-id / x-bitwarden-client-secret | for member/group tools | unchanged |
| x-bitwarden-user-client-id | for the Send tool | personal API key client_id of the sending member account (`user.<uuid>`) |
| x-bitwarden-user-client-secret | for the Send tool | its client_secret |
| x-bitwarden-master-password | for the Send tool | master password of that account, used in memory to unlock the account key for this request only |
| x-bitwarden-api-url / x-bitwarden-identity-url | optional | unchanged (EU / self-hosted) |

No database, no migration.

### Key flow / sequence

1. Middleware stores the request's headers in the contextvar (no 401 if the user triple is complete).
2. Tool validates arguments (AC5); missing user triple → `missing_credentials` (AC6).
3. `POST {identity}/connect/token` with the user API key; `deviceIdentifier` = UUIDv5 of the client_id (stable per account, no device sprawl, still stateless).
4. From the token response take `Key` (protected user key) and `Kdf`, `KdfIterations`, `KdfMemory`, `KdfParallelism`; email from `GET {api}/accounts/profile`.
5. Master key = PBKDF2-SHA256(password, email) or Argon2id(password, SHA256(email)); stretch with HKDF-Expand (`enc`, `mac`); verify MAC and decrypt the user key (MAC failure → `unlock_failed`).
6. Seed = 16 random bytes; Send key = HKDF-SHA256(seed, salt `bitwarden-send`, info `send`, 64 bytes); encrypt name and secret with the Send key, the seed with the user key.
7. `POST {api}/sends` with the access token; read `id` and `accessId` from the response.
8. Return the link and metadata; all key material goes out of scope with the request.

### Non-functional

- Security: the secret, master password, master key, user key and seed exist only in local variables for one request; nothing is cached, written to disk or logged (no logging calls take arguments, headers or bodies; error messages are built from status + Bitwarden's `message` only). The link itself contains the seed by design; it is the deliverable. The secret argument is named `secret` so the platform's name-based masking hides it in approvals and run detail.
- Tenant isolation: per-request contextvar, as today. No module-level state.
- Idempotency: each call creates a new Send; the agent must not retry blindly after a success. The tool description says so.
- Performance: two Identity/API round trips plus one KDF. PBKDF2 at Bitwarden's default 600,000 iterations takes roughly 0.3-0.6 s in Python's hashlib; Argon2id default (64 MiB, 3 iterations) similar. Acceptable for about 38 calls a month.
- Logging / observability: one info line per call with tool name, HTTP status and Send id only.

### Rollout & rollback

- Release order: single MCP repo, `any`. Backward compatible: existing tenants send only the org headers and see no change (the middleware still accepts them; the 401 rule is only widened).
- Before the Send tool is usable on INT, the three credential fields must exist on the `bitwarden` vendor in the control plane (Leo Yang). Without them the tool deploys fine but tenants cannot enter the credentials.
- Rollback: redeploy the previous `main` commit; no data to migrate.

### Risks & dependencies

- Control-plane dependency (handed to Leo Yang): add three credential fields to the registered `bitwarden` vendor (`mcpm_vendor_registry.credential_fields`, edited through admin-console or `vendor-deploy.sh register`, see `mcp-service-gateway@0296cc8 DEPLOY.md:88`, `:137`, `:206`). The pipeline's publish API only deploys `main` and never updates credential fields of an existing vendor. Proposed fields (all optional, type password for the secrets):
  `{"x-bitwarden-user-client-id": {"label": "Send: User API Client ID", "type": "str", "required": false}, "x-bitwarden-user-client-secret": {"label": "Send: User API Client Secret", "type": "password", "required": false}, "x-bitwarden-master-password": {"label": "Send: Master Password", "type": "password", "required": false}}`
- Security decision (Leo Yang): storing a Bitwarden master password as a gateway credential. It is encrypted per record in the credential store like any other secret, but it unlocks that account's whole vault. Mitigation written into the README: use a dedicated member account that holds no vault items and exists only to send. Alternative if this is not acceptable: no stateless way exists (Option B/C above).
- Accounts without a master password (SSO with Key Connector, trusted-device encryption) cannot be used; the tool returns `unsupported_account`.
- Bitwarden may change the Send or login protocol; the crypto follows the current open-source clients.
- Organization policies "Remove Send" or "Send options" on VIP IT's organization would make Bitwarden reject the Send; surfaced as `bitwarden_error` with Bitwarden's message.

### Decisions made by DEV01

- Extend the existing `bitwarden-mcp` instead of a new repo — one connector per product; alternative: a separate `bitwarden-send-mcp` vendor (Option D).
- Stateless per-request login + in-memory unlock with a master password header — the only way to create a Send without a stateful CLI vault; alternative: `bw serve` (Option B).
- Header names `x-bitwarden-user-client-id`, `x-bitwarden-user-client-secret`, `x-bitwarden-master-password` — one field per header as the SOP requires; alternative: reuse the existing client-id header for a `user.` key, rejected because it would break the member/group tools for that tenant.
- The secret is passed in, not generated — follows the intake comment; alternative: a `generate` flag, not asked for.
- Defaults expiry 24 h, access count 1, deletion after 30 days; limits 1..720 h and 1..100 accesses — safe defaults for one-time credential delivery, deletion kept later than expiry so the Send stays visible for audit; alternative: delete at expiry, rejected because the audit trail would disappear.
- Stable `deviceIdentifier` derived from the client_id — avoids one new "device" per call on the account without keeping state.
